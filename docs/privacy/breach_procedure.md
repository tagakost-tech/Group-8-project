# Personal-data breaches (outline)

Status: outline for counsel, due now: step G16 is built. It describes the agent as handed to SUPPLECO in November 2026. Art. 33(1) requires notifying the supervisory authority without undue delay and, where feasible, within 72 hours of becoming aware of a breach, unless the breach is unlikely to result in a risk to people. Art. 33(5) requires every breach to be documented, notified or not. Art. 34 requires telling the people affected when the risk to them is high.

## Breaches this product could suffer

- **The machine is lost or stolen.** The database and every store listed below are on its disk, and the product encrypts none of them. Disk encryption on the host (decision I4) decides the risk.
- **The database is copied.**
  - It holds every contact not yet erased in clear. The do-not-contact list holds opt-outs, bounces, mail-server rejections and operator blocks as plain addresses, and company blocks are plain domains, except those an erasure left.
  - An address erased on request is kept only as a keyed token (step G7), and a company blocked after an erasure only as a keyed domain token (G5c). Without the erasure key, the tokens themselves reveal nothing. A request made by reply also counts as an opt-out, so the requester's address stays on the do-not-contact list in clear, as any opt-out does, until `main.py dsr erase` runs for an erasure request (L5.5).
  - An erased person leaves, beside the token: the score, tier, verification flag, source channel, basis, rules version, search link and dates on the contact row; the sending mailbox, message id, delivery result, notice version and dates on each email record, whose subject and text read "[erased]"; its follow-up and retry records; and any request in the register, under the token. Activity entries that name the company without the person's address stay too (L5.2). The G18 registry (`PERSONAL_COLUMNS` in `modules/compliance.py`) lists what an erasure does with every column.
  - After a restore, an email sent to an address the restored backup does not hold is kept in the table `prior_sends` under the address's keyed token, never the address: the token, the message's id, the time, the delivery result, the follow-up step, the sending mailbox and the notice version. Without the erasure key the token reveals nothing. The row becomes an ordinary email record if that address is collected again.
  - An erasure on request deletes the daily send counts of the person's company domain. A retention erasure leaves them until they are deleted after 30 days.
  - Erased values are zeroed inside the database file, and its write-ahead log is emptied after each erasure and retention run (step G8). If another connection holds the log open, the next run empties it, and the preflight check (`main.py doctor`) warns meanwhile.
- **A store beside the database is copied.** These are in `data/`, beside the database:
  - `backups/`: the newest 14 full copies of the database (step G16). Each holds in clear everyone erased after it was made, until it is replaced.
  - `journal.jsonl`: in clear, every address that opted out, was blocked or unblocked on the dashboard, bounced or was refused by its mail server, and every blocked company domain, kept so that a restore cannot undo them. An erasure is written only as its token, and it rewrites that person's earlier lines as tokens. The journal also holds every data-subject request registered or closed. It also holds one line for every email sent: the recipient's address in clear, the message's id, the follow-up step if it was one, the time, the sending mailbox, the notice version, and whether the server's answer was lost. It holds no subject and no text. So a copied journal shows who SUPPLECO emailed since the oldest backup, and when. An erasure rewrites these lines as the token too. It is trimmed to the oldest backup (G16).
  - `exports/access-<code>/`: an access answer, which holds the database's records about one person (`records.json`) with its cover letter. It is kept up to 30 days after it was written, and deleted at once if the person is erased on request (G11, G12).
  - `spool/optouts/`: opt-outs, declines, company blocks and data requests that met a busy database, held until they are applied, with the address in clear (G5b, G5c, G11). A click the database was too busy to look up is held as the link's code, and one that then matched no link record is kept as that code only, for up to a year (G20).
- **The log files are copied.** `logs/` holds one file per command, rotated at midnight; the newest 30 old files are kept (`LOG_RETENTION_DAYS`), which is 30 days for a command run daily. An address is masked to its first letter and domain when written, and unsubscribe tokens and IPv4 and IPv6 addresses are replaced (step G9). Keys and passwords a library puts in an error message are replaced too.
- **The settings file (`.env`) is exposed.**
  - It holds the mailbox credentials, the dashboard password, the own AI server's key (`LLM_API_KEY`) if one is set, the secret behind the unsubscribe links (`UNSUBSCRIBE_SECRET`), and the erasure key (`ERASURE_KEY`). With Microsoft sign-in set up it holds no Microsoft 365 mailbox password: the mailboxes sign in with the certificate in `MICROSOFT_CERTIFICATE_PATH` (and its passphrase, if one is set).
- **The Microsoft sign-in key is copied** (the file in `MICROSOFT_CERTIFICATE_PATH`). Whoever holds it can read and send mail as the mailboxes IT gave the app. Delete its certificate in Microsoft Entra (the app registration, Certificates & secrets) at once: that stops every sign-in with it. Then make and upload a new one (`docs/DEPLOY.md` section 12), and check the mailboxes' sent items and sign-in logs for the time it was exposed.
  - The old form of opt-out link (the encoded address and a signature), which the secret could make for any address, is refused. A link in the current form carries a keyed code of the address, and the agent honours any code it recorded when it sent the email, whatever secret made it (`modules/unsubscribe.py`). So the secret also forges a working link for every address the agent has emailed, until that contact is erased, on request or by retention, which deletes its link records.
  - A forged link opts the person out, and a forged one-click request also blocks their company. That errs on the person's side, but it changes their records without their say: assess it in step 3 as a risk to the integrity of the data. The page a click opens says whether the link matched someone the agent emailed, so the secret also lets someone test whether SUPPLECO emailed a guessed address.
  - Rotate the credentials, the own AI server's key if one is set, and the unsubscribe secret. A new secret protects only the links made after it: links already sent keep working, for their owners and for whoever holds the old secret, until their records are deleted. Objections by email still work if inbox reading is on.
  - A rotation also loses the clicks set aside because they matched no link record (after a restore from an older backup). The send check looks for a recipient's set-aside click under the code the current secret makes (`modules/dispatch_pipeline.py`), so after a rotation it no longer finds a click on a link made before it. The preflight check's "Held opt-outs" line counts these clicks. Whether the code should also look under the old secret's code is for the developer to decide; nothing is built.
  - The erasure key cannot be replaced: the database refuses a different key (L5.10). Someone holding both the key and the database, or a backup, could confirm, for good, whether a guessed address was erased. `docs/DEPLOY.md` (section 6) says to treat a leaked key as a breach. Counsel is asked whether a key that cannot be replaced is acceptable (L5.10).
- **A lead alert or an access answer goes to the wrong person.** A lead alert carries the person's address and up to 1,500 characters of their reply. An access answer holds the database's records about one person.
- **Someone uses the dashboard who should not.**
  - The dashboard refuses to start without a `DASHBOARD_PASSWORD` of at least 12 characters, wherever it listens, the local machine included, and the preflight check fails on the same rule. It never runs Flask's debugger.
  - One address that types 10 wrong passwords within 15 minutes is shut out until the oldest is 15 minutes old. The log says when this happens; a burst of 401 and 429 answers in the log is a sign someone is guessing.
  - Anyone who knows the password can read the contacts, send email and change settings. A leaked password is a breach to assess: change `DASHBOARD_PASSWORD` and restart the dashboard.

## Steps

1. Contain the breach (`docs/INCIDENT_PLAYBOOK.md` says how, for the operator and IT). Record when SUPPLECO became aware of it.
2. The same day a breach is suspected, tell the privacy contact (L2.6). The developer reports any breach they find within 24 hours (L2.9).
3. Assess the risk to the people affected: what data, how many people, and whether it is protected (encrypted or keyed). The list above says what each store holds.
4. Within 72 hours where feasible, notify the Garante, unless the risk is unlikely. Counsel decides. Since 1 July 2021 a notification can be filed only through the Garante's online procedure on servizi.gpdp.it (provvedimento n. 209 of 27 May 2021, doc. web 9667201). The review found how the person filing identifies themselves (SPID or CIE, or a digitally signed notice) only in secondary sources: check it in the portal's instructions. Who at SUPPLECO files, and how they sign, is open (L2.6, L2.9).
5. If the risk is high, tell the people affected (Art. 34).
6. If the database has to be restored, restore it as below before the agent or the dashboard runs again.
7. Record the breach in the register below.

## Restoring the database

- Stop the agent and the dashboard, copy a backup over `data/agent.db`, delete `data/agent.db-wal` and `data/agent.db-shm`, and run `main.py replay-journal` before anything else (`docs/DEPLOY.md`, section 9). It re-applies every opt-out, company block and lift, dashboard Block and Unblock, bounce and erasure recorded since the backup, in the order they happened, erases again everyone erased on request since (and replaces the domain of an erased person's company with its code in the activity log, deleting its daily send counts), and then, while `RETENTION_ENABLED` is on, runs retention to erase again what retention erased since.
- A request registered or closed since the backup is kept, and a link in an email sent since the backup still works after the replay.
- The replay needs the journal and the same `ERASURE_KEY`. Without the journal, a backup brings back everyone erased since it was made, loses every opt-out, block and bounce made since, and forgets every email sent since, so people would get the same email twice. The journal sits beside the database, so a disk lost with both leaves nothing to replay. Where a second copy of the journal could be kept is for IT to choose (I4).
- The replay also puts back every email sent since the backup, from its journal line: the contact counts as emailed at the time the email went, a follow-up step that went is moved on, and today's counts per company domain and mailbox include it. So no one gets the same first email or follow-up twice. An email to an address the backup does not hold is kept under the address's keyed token, and that address starts as already emailed if the agent collects it again. The replay starts no follow-ups for anyone (`docs/DEPLOY.md`, section 9, "What a restore still cannot bring back").
- Before restoring, `main.py restore-drill --newest` (or `--backup <file>` for another copy) restores the backup in a temporary folder, replays the journal there, and fails if any opt-out, company block, address block, bounce, erasure, held opt-out or email sent would be lost (it counts each kind separately) or anyone erased would come back. After the restore and the replay, `main.py restore-drill` checks the result. The steps for the first hour and day are in `docs/INCIDENT_PLAYBOOK.md`, incident 4.
- If the backup restored was the newest, `main.py restore-check` then repeats the replay on a scratch copy of it, without touching the live database, and fails if the copy is damaged or still holds an address the live database no longer holds in clear.
